GitHub Copilot: I'll explain what `.trigger(...)` does and give short examples and alternatives.

- What it does: `.trigger(processingTime="5 seconds")` tells Spark Structured Streaming to run the query in periodic micro-batches, scheduling a new batch every 5 seconds (equivalent to `Trigger.ProcessingTime("5 seconds")`). The first batch runs as soon as work is available; subsequent batches run at the given interval.

- Programmatic form:
```python
from pyspark.sql.streaming import Trigger

parsed_query = (
    parsed_df.writeStream
    ...
    .trigger(Trigger.ProcessingTime("5 seconds"))
    .start()
)
```

- Other useful triggers:
  - `Trigger.ProcessingTime("N seconds")` — periodic micro-batches (default pattern).
  - `Trigger.Once()` — run a single micro-batch that processes all available data then stop.
  - `Trigger.AvailableNow()` — process all currently available data and stop (useful for ingestion catch-up jobs).

- Practical notes:
  - Shorter intervals → lower latency but higher scheduling/overhead; longer intervals → better throughput.
  - Checkpointing (`checkpointLocation`) is still required for durable recovery with most sinks.
  - Use `Trigger.Once()` or `AvailableNow()` for one-off batch-style runs; use `ProcessingTime` for continuous micro-batch streaming.

Summary — short answer
- Yes, the high-level architecture is sensible (Kafka → Spark Structured Streaming → persist).  
- Improvements: avoid intermediate JSON files, use proper Spark schema types, write streaming directly to Iceberg (or use foreachBatch), handle parsing failures and timezones, and use checkpointing for exactly-once.

Key issues & recommendations
- Schema type: `TIMESTAMP_NTZ` is not a Spark DataType. Use Spark `TimestampType` (or build a `StructType`) instead of vendor-specific types. Build the schema with a `StructType` to avoid ambiguity.
- from_json schema: pass a `StructType` (or DDL wrapped in `struct<...>`) to `F.from_json` to ensure correct typing.
- Don’t write streaming Kafka -> JSON files -> static read -> write to Iceberg in production: it’s brittle (partial files, race conditions, many small files). Instead:
  - Write streaming directly into Iceberg (if supported by your Spark/Iceberg combo) via a streaming sink, or
  - Use `foreachBatch` to perform transactional writes to Iceberg per micro-batch (recommended if Iceberg sink integration isn't available).
- Checkpointing: you already set a checkpoint for JSON sink — keep a checkpoint when writing to Iceberg too (for streaming sinks). For `foreachBatch`, still use `writeStream(...).option("checkpointLocation", ...)`.

Why duplicates happen (short)
- If a micro-batch is retried (job crash, driver fail), `foreachBatch` may re-run the same batch; `writeTo(...).append()` will re-insert unless the sink is idempotent.
- Checkpointing prevents reprocessing of Kafka offsets only if the checkpoint is durable and used; transient checkpoints or manual re-runs can replay.

Recommended fixes (choose one)
1) Idempotent dedupe in foreachBatch (simple, reliable)
   - In each batch, filter out rows already present by matching on a unique key (e.g., `partition`+`offset` or a message id).
   - Good for small-to-medium workloads.

2) MERGE/Upsert into Iceberg (robust)
   - Create a temp view for the batch and run `MERGE INTO` on unique key (partition+offset). Atomic and best if Iceberg version supports merge.

3) Track high-water offsets per partition (efficient)
   - Persist max offset per partition after each successful batch and only write rows with offset > stored_max. Requires transactional update of the offsets store.

GitHub Copilot: I'll explain what `.trigger(...)` does and give short examples and alternatives.

- What it does: `.trigger(processingTime="5 seconds")` tells Spark Structured Streaming to run the query in periodic micro-batches, scheduling a new batch every 5 seconds (equivalent to `Trigger.ProcessingTime("5 seconds")`). The first batch runs as soon as work is available; subsequent batches run at the given interval.

- Programmatic form:
```python
from pyspark.sql.streaming import Trigger

parsed_query = (
    parsed_df.writeStream
    ...
    .trigger(Trigger.ProcessingTime("5 seconds"))
    .start()
)
```

- Other useful triggers:
  - `Trigger.ProcessingTime("N seconds")` — periodic micro-batches (default pattern).
  - `Trigger.Once()` — run a single micro-batch that processes all available data then stop.
  - `Trigger.AvailableNow()` — process all currently available data and stop (useful for ingestion catch-up jobs).

- Practical notes:
  - Shorter intervals → lower latency but higher scheduling/overhead; longer intervals → better throughput.
  - Checkpointing (`checkpointLocation`) is still required for durable recovery with most sinks.
  - Use `Trigger.Once()` or `AvailableNow()` for one-off batch-style runs; use `ProcessingTime` for continuous micro-batch streaming.
